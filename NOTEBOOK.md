## Pitfalls

What went wrong and how to avoid it.

- A UI that marks choices and applies them on a later button (the spell store's Accept) loses everything when the mod's own key closes it: buy through the game's message instead of the screen. Read the screen's callbacks (names "AptX::OnBttn..." in game.dat) before clicking it.
- windows.h defines `near` and `far` as macros: a variable named near breaks the build with a bare "syntax error: ." (met twice, last 2026-11-15 in wotr.cpp; use `nearby`).

- An area is usually lifted by several scripts, one of them a late cinematic that lifts everything: picking the opener by the shortest walk back names that cinematic. Rank openers by how much story comes before them, and drop those that need a walk into the area itself.
- "Destroy the nearest" is wrong where each target opens the wall to the next one (Dead Marshes): read the map's checkpoints or walls for the order and give the guide an ordered "attack = ... | x y; x y" list.
- Script has no name field in this build, only three comments: look a name up from its table, or from the team's prototype. A log line that prints what was read saved a whole round of guessing.
- A team runs its own copy of a generic script: DISABLE_SCRIPT and the original's active byte do not reach it, and making the copy inactive drops it from the team for good. Answer in the evaluator instead.
- Anything that walks a unit along a script path ignores the mission's walls and can break the story for good. Never do it automatically.
- "No script chain names it" does not mean unneeded: a pick-up or walk can open an impassable area. Before writing an object off, grep what its script does, not only what tests it.
- Every new filter hides something real sooner or later: keep what stands near the player's own units.
- A script chain ends at a team's on-destroyed script: triggers.py sees no setter and the objective gets no place (Rescue the Fellowship). A game's light can stand for the end of the mission, not the next step.
- An objective can stay open or come back across episodes. A guide with a map path or a hand place must be read against who can stand there in each episode; never give a path to a "Speak to X" objective.
- g_guides holds every mission's tags: any rule over all guides must first test that the tag is in this mission.
- Each new feature needs a log word to search for: "сюжет" never spoken in a day of tests was the proof of a dead condition. After a deploy, grep the log for the feature's word.
- A generated guide can lose what its tracer found: after a generator change, diff the new guides-auto.ini against the old and read what vanished, and look for a filter by side or depth. The side of an object says who holds it, not who must act.
- A Python heredoc through the Bash tool can turn \\b in a patch into a real backspace: a regex silently matched nothing. Write patch scripts with the Write tool.
- Speak(text, true) clears the queue, so a line said just before it is lost and not even logged: the second of two lines must use interrupt false.
- One worker thread runs all the mod: an endless loop anywhere silences everything with no crash report. The last log line tells where it stopped.
- detect-engine.ps1 reported "scripted, Lua (embedded), 64-bit, AotR_Launcher.exe": wrong. It saw scripts.lua and the 64-bit launcher. The engine is native SAGE, 32-bit, in rotwk\game.dat.
- AotR launcher 2.0 file scan lists unknown rotwk files for removal ("Delete: winmm.dll", "Delete: scripts/AotRAccess.asi", app.log 2026-10-31 20:33:09) when it patches ROTWK. They were not removed that day, but after any launcher patch check that both files are still there (deploy.ps1 puts them back).
- Game menus do not react to arrows or other keys (player, 2026-10-31): mouse only. The player used to click some menus with NVDA OCR and played battles by ear with many in-game hotkeys. After our deploy, OCR clicks in menus did not work. The player installed AotR 10.0 on 2026-10-31 (after removing 9.x) and had never used OCR on 10.0, so the old OCR experience was on 9.x. Cause not known yet: our winmm.dll, Tacitus (new with 10.0: DPI fix, window moves, D3D hooks) or the AotR 10.0 UI. Test: one launch with winmm.dll renamed to winmm.dll.off.
- gh CLI is not authenticated on this PC: use curl on api.github.com (60 requests per hour) or raw.githubusercontent.com.
- AotR launcher "Campaign Update Required" dialog: accept it only for real 9.x autosaves. It adds 1 to the mission index of every autosave without Debug_TEST, also of a correct 10.0 autosave written from a 9.x chain (Council of Elrond, 2026-11-01 08:38:52). Old 9.x manual saves loop the mission after the one where 10.0 inserted a mission.
- The Bash tool halves backslashes inside heredocs: a Python patch written in a heredoc silently misses text with \\ (LoadGuides, 2026-11-04). Write patch scripts with the Write tool and assert every match.
- "Player_1 is the player" holds only on story maps: the War of the Ring missions use Player_2. Any tool or mod code that names a side must ask Mission.me (tools) or the live local player (mod).
- SAGE map conditions can be inverted (u32 at the end of a Condition v6): a reader that drops it turns "NOT hidden" into "hidden". mapfile.py gives s['not'] now; read every condition with it before deciding what a script does.
- A bash heredoc command that begins with a bare `cat > file` without its own heredoc waits for stdin and hangs until the 2-minute timeout: write scratch scripts with the Write tool.
